# Hops — System Design

A small Slack-like messaging app built around one question: **what deserves someone's attention, and how does it reliably get to them?**

Each section is written as *decision → why → what I rejected*. Things I chose not to build are listed explicitly in §8.

---

## 1. Summary

| Decision | Choice |
|---|---|
| Architecture | Modular monolith (one Node process: API, WebSocket, worker) |
| Stack | TypeScript, React + Vite, Fastify, `pg` + plain SQL, `ws` |
| Source of truth | PostgreSQL |
| Getting changes to other systems | Transactional outbox + per-consumer delivery rows |
| Event shape | Thin events (`{messageId}`); consumers load current state |
| Consumers | Search (fake, external), Notifications (fake, external), Activity feed (local projection) |
| Delivery | At-least-once; consumers are idempotent and don't depend on event order |
| Realtime | WebSocket, best-effort; the database is authoritative |
| Deletes | Soft delete (tombstones) everywhere, including search |
| Client | Optimistic UI with IDs generated by the client |

```
 React UI ──HTTP──► API ──one transaction──► Postgres
    ▲                │                         │ domain rows
    │                │ after commit            │ outbox_events
    └──WebSocket─────┤                         │ event_deliveries (one row per consumer)
                     │                         ▼
                     │                 Worker (claims due deliveries)
                     │            ┌────────────┼──────────────┐
                     │            ▼            ▼              ▼
                     │     Search (fake)   Activity       Notifications (fake)
                     │     latency+faults  projection     latency+faults, grace delay
                     └──── activity.changed ◄──┘
```

**Why a monolith:** the brief is about guarantees and product craft, not deployment. The fakes sit behind interfaces that behave like network calls: they add random latency and inject failures, and the code only reaches them through a client object. Splitting them out later would change the transport, not the design.

## 2. Product decisions

### 2.1 What I borrowed and what I changed

- **Slack (primary reference):** channels, DMs, threads, `@mentions`, the "(edited)" label, "This message was deleted."
- **GitHub notifications:** every activity item shows a **reason** (*mentioned you*, *DM*, *replied in a thread you're in*, *reacted*). That makes "why am I seeing this?" obvious.
- **Linear inbox:** a single inbox with clear read/unread state and grouping. It's easy to triage.
- **Changed from Slack:** Slack spreads attention across Activity, Threads and DMs, and its Activity tab is noisy. I use **one unified feed** with grouping so it stays quiet.

### 2.2 Activity vs notification

- **Activity** is *everything relevant to you*. You look at it when you choose to.
- **Notification** is *something directed at you* that is worth interrupting you for. It is a subset of activity.

Both come from one function, so the rules can't drift apart:

```ts
computeRecipients(message) → Array<{ userId, reason, alert: boolean }>
```

| Trigger | Recipient | Reason | Activity | Notify (`alert`) |
|---|---|---|---|---|
| `@mention` (user is a channel member) | mentioned user | `mention` | ✅ | ✅ |
| DM message | other DM members | `dm`, grouped per conversation | ✅ | ✅ |
| Thread reply | thread subscribers | `participating` | ✅ | ❌ |
| Reaction | message author | `reaction`, grouped per message | ✅ | ❌ |

Rules:
- **Never for your own actions.** You don't get activity for replying in your own thread or reacting to your own message.
- **One item per user per message.** If rules overlap, the highest priority wins: `mention > dm > participating > reaction`. A reply that @mentions you appears once, as a mention.
- **Thread subscribers** are the root author, anyone who replied, and anyone mentioned in the thread. This matches Slack. The subscription is stored in the same transaction as the reply or mention, because it is source data, not a projection.
- **Mentions of non-members are ignored.** No activity, no notification.
- **Thread replies don't notify.** Slack does notify for these by default. I left them as activity only to keep interruptions for things aimed directly at you. This is a deliberate choice.

### 2.3 Grouping

| Group | Key | Displayed as |
|---|---|---|
| Reactions on my message | `reaction:{messageId}` | "Alice, Bob and 3 others reacted 👍 ❤️ to *…*" |
| DM conversation | `dm:{channelId}` | "Alice sent you 3 messages" + latest preview |
| Mention / thread reply | `msg:{messageId}` | one item per message |

A group becomes **unread again** when something new arrives (`latest_at` advances). Edits don't make it unread.

### 2.4 Stale, edited and deleted entries

The feed stores **references, not snapshots**. Each item is rendered from the *live* message when it's read, so it can't show outdated text.

| Situation | What the user sees | How |
|---|---|---|
| Message edited | Current text + "(edited)" | Live join at read time |
| Message deleted | Item **hidden** | Read-time filter `status <> 'deleted'` |
| Thread root deleted | Reply items stay; root shows "This message was deleted." | Only activity *about* the deleted message is hidden |
| Mention removed by an edit | Mention item hidden | Read-time check that the `mentions` row still exists; the consumer then recomputes (you may still be listed as a participant) |
| Reaction removed | Group shrinks; removed entirely when empty | Consumer recomputes the group |

**Why filter at read time as well as in the consumer:** the feed is correct as soon as the delete commits, even if the activity consumer is behind or retrying. The unread badge uses **the same query**, so it can never say 3 when only 2 items are visible.

### 2.5 Read state

- Clicking an item marks it read and opens the message in context (channel scrolled to it, or the thread panel).
- "Mark all as read".
- *Cut:* automatically marking items read when you view the message in a channel (§8).

### 2.6 Notification policy

- Only recipients with `alert = true`: mentions and DMs.
- **Grace delay:** the notification delivery is scheduled for `created_at + GRACE` (10s for the demo, configurable).
- When it's time to send, the consumer **reloads the message**:
  - Deleted → skip. Not sending is treated as success.
  - My mention was removed → skip.
  - Edited → send the latest text.
- **Staleness:** events older than 15 minutes are dropped. After an outage, nobody gets a flood of notifications from an hour ago. This also stops seeding from sending notifications.
- **Idempotency key** `messageId:userId` is passed to the sender. Retries and edits don't notify twice, but a mention *added* by an edit does notify.
- **Honest limit:** a notification can't be recalled once sent. "Deleted within the grace period, so never sent" is the guarantee. There is also a small gap between the final check and the send.

## 3. Data model (`schema.sql`, plain SQL)

```sql
users(id uuid PK, handle text UNIQUE, name text, avatar_url text)

channels(id uuid PK, name text, kind text CHECK (kind IN ('public','dm')), created_at)
channel_members(channel_id, user_id, PRIMARY KEY (channel_id, user_id))

messages(
  id uuid PK,                 -- generated by the client (UUIDv7) → create is idempotent
  channel_id, author_id,
  parent_id uuid NULL,        -- a reply is just a message with a parent
  body text,
  status text CHECK (status IN ('active','deleted')),
  version int NOT NULL DEFAULT 1,
  created_at, edited_at NULL
)
  INDEX (channel_id, created_at, id)
  INDEX (parent_id, created_at)

mentions(message_id, user_id, PRIMARY KEY (message_id, user_id))
reactions(message_id, user_id, emoji, created_at, UNIQUE (message_id, user_id, emoji))
thread_subscriptions(root_id, user_id, PRIMARY KEY (root_id, user_id))

activities(
  id uuid PK, user_id,
  group_key text,             -- msg:{id} | reaction:{id} | dm:{channelId}
  reason text,                -- mention | dm | participating | reaction
  message_id, channel_id,
  actor_ids uuid[], count int,
  latest_at timestamptz, read_at timestamptz NULL,
  UNIQUE (user_id, group_key)
)
  INDEX (user_id, latest_at DESC)

outbox_events(id bigserial PK, type text, message_id uuid, payload jsonb, created_at)  -- never modified after insert

event_deliveries(
  event_id, consumer text,    -- search | activity | notifications
  status text,                -- pending | done | dead
  attempts int, next_attempt_at, locked_until NULL, last_error NULL, done_at NULL,
  PRIMARY KEY (event_id, consumer)
)
  INDEX (status, next_attempt_at)

-- Owned by the fakes and only accessed through their client interfaces.
-- They stand in for external systems' own storage.
fake_search_docs(id uuid PK, version int, deleted bool, body text, channel_id uuid)
fake_notifications_sent(idempotency_key text PK, user_id, body text, sent_at)
```

**Rejected:**
- A `processed_events` table. It duplicates `event_deliveries`, and it can't protect external calls anyway. See the per-consumer guarantees in §6.
- Retry state on `outbox_events` itself. Consumers succeed and fail independently, so retry state belongs on each delivery.

## 4. How a change gets to the other systems

### 4.1 Write path

Every write runs in **one transaction**. Writes are create, edit, delete, and reaction add/remove.

```
BEGIN
  domain rows (message / mentions / thread_subscriptions / reactions)
  INSERT outbox_events (type, message_id)
  INSERT event_deliveries × 3            -- notifications: next_attempt_at = now() + GRACE
COMMIT
→ broadcast over WebSocket (after commit, best-effort)
```

- **Events:** `MessageCreated`, `MessageEdited`, `MessageDeleted`, `ReactionChanged`. The payload is just `{messageId}`.
- **Create is idempotent:** `INSERT … ON CONFLICT (id) DO NOTHING` and return the existing row. Returns 409 if the ID belongs to another author. A retried POST can't create a duplicate message.
- **Edit uses optimistic concurrency:** the client sends `expectedVersion`. A mismatch returns 409. Only the author can edit or delete.
- **Delete** sets `status = 'deleted'` and `version + 1`. The row is kept because replies, activity and search all reference it.

**Why thin events:** consumers always act on the *current* state. A late retry of an old event can't push old data anywhere. Search and notifications both rely on this. **Rejected:** fat events. They are self-contained, but they carry old data and need careful ordering.

### 4.2 Worker

- A **single-flight** loop every 250ms: the next tick doesn't start until the current one finishes.
- **Claiming** is safe even with several workers:

  ```sql
  UPDATE event_deliveries SET locked_until = now() + interval '30 seconds'
  WHERE (event_id, consumer) IN (
    SELECT event_id, consumer FROM event_deliveries
    WHERE status = 'pending' AND next_attempt_at <= now()
      AND (locked_until IS NULL OR locked_until < now())
    ORDER BY next_attempt_at LIMIT 20
    FOR UPDATE SKIP LOCKED)
  RETURNING *;
  ```

  If a worker crashes, its lease expires and another worker picks the delivery up.
- Each consumer handles its own deliveries. A failing search index **doesn't block** activity or notifications.
- **Success** → `status = 'done'`.
- **Failure** → `attempts + 1`, `next_attempt_at = now() + min(2^attempts s, 5 min) + jitter`, and the error is recorded.
- **After 10 failed attempts** → `status = 'dead'`. Visible at `GET /debug/deliveries`.

### 4.3 Consumers

**Search (external):**
1. Load the message.
2. Call `search.index({ id, version, deleted, body, channelId })`.
3. The fake applies the write **only if `version > stored.version`**, like Elasticsearch's `version_type=external`.
4. A delete stores a **tombstone**, not a real delete. Without it, a late retry of v3 after the v5 delete would put the message back in search.
5. `GET /search?q=` excludes tombstones and channels the user isn't a member of, so DMs stay private.

**Activity (local projection):**
1. Recompute the groups this message affects **from the source of truth**. For example, a reaction group is rebuilt from the current `reactions` rows, not from counting events. That makes it idempotent and independent of event order.
2. Upsert or delete the `activities` rows **and mark the delivery done in the same transaction**. The result: each event takes effect exactly once.
3. `read_at` is kept unless `latest_at` advances.
4. After commit, push `activity.changed` over WebSocket to the affected users.

**Notifications (external):** follows the policy in §2.6.

**Why the activity feed is local but still behind the outbox:** it's the one consumer that can share a transaction with its delivery state, and that gives the strongest guarantee in the system. It stays asynchronous and separated so it could become a separate service later without redesign.

## 5. Realtime and optimistic UI

### 5.1 WebSocket

- Connect with `WS /realtime?as=<userId>`. The server subscribes the socket to all the user's channels plus a personal user topic.
- **After commit**, the API broadcasts:
  - `message.upserted`: the full message, including `version`.
  - `reactions.updated`: **absolute** counts, never ±1 changes, so duplicate events are harmless.
- The activity consumer sends `activity.changed` to the user topic.
- Clients apply a message only if `incoming.version >= local.version`.
- **On reconnect**, clients refetch the current channel and the activity feed. There is no replay of missed events.
- **Guarantee:** best-effort. The database is authoritative, and a refresh always shows the truth.

### 5.2 Optimistic UI

| Action | Optimistic behaviour | Reconciliation |
|---|---|---|
| Send | Client generates a UUIDv7 and shows the message as *pending* | The server response or WebSocket echo has the **same ID**, so it replaces the pending copy. On failure: *failed*, with retry/discard. Retrying is safe because create is idempotent. |
| React | Toggle immediately | The server returns absolute counts. On error, undo. |
| Edit | Show the new text immediately | On 409, undo and refetch |
| Delete | Show the tombstone immediately | On error, undo |

If time runs short: send and reactions first, then edit and delete.

### 5.3 Client state

`messagesById` plus separate ordered ID lists per channel and per thread. Realtime updates replace one entry by ID instead of rewriting nested component state.

## 6. Guarantees

| Guarantee | Mechanism | Not guaranteed |
|---|---|---|
| A message is durable once the API returns 201 | Single Postgres transaction | — |
| Retried creates don't duplicate | Client-generated ID + `ON CONFLICT` | — |
| Every committed change reaches every consumer **at least once** | Outbox + delivery rows in the same transaction; retries with backoff | Latency: consumers catch up *eventually*. After 10 failures a delivery is marked `dead` and needs a manual replay (UI cut). |
| Activity processes each event **exactly once** | Projection write + delivery marked done in one transaction; recompute from source | — |
| Search **converges to the latest version** | Thin events, writes that only apply if the version is newer, tombstones | Search may be briefly behind |
| No duplicate notifications | Idempotency key `messageId:userId` honoured by the sender | — |
| No notification for a message deleted within the grace period | Delayed delivery + check of current state before sending | **Can't recall** a sent notification; a small gap exists between the check and the send |
| Consumers don't depend on ordering | Versions + recompute from current state | **No global ordering** of events |
| Realtime updates | WebSocket after commit | **Best-effort**: can drop events; the client refetches on reconnect |

## 7. Seed data

About 20 users, 8 public channels, a handful of DMs, and about 500 messages, with:
- **Realistic timestamps:** a few in the last 5 minutes, then the last hour, today, and the past week.
- Replies, reactions, mentions, some edits and deletes.

**Seed through the domain service, not bulk SQL.** The outbox then fills the search index and activity feeds naturally. The seed can override `createdAt`, and the 15-minute staleness rule stops notifications from being sent for old seeded messages. Seeding like this also shows how a projection can be rebuilt.

## 8. Deliberately not built

| Cut | Why it's acceptable / what I'd do instead |
|---|---|
| Pagination | Load the last 100 messages; the `(created_at, id)` index is already there for cursor pagination |
| Dev control panel | Fault rates via env vars (`SEARCH_FAILURE_RATE`, `NOTIFY_FAILURE_RATE`, latency) + `GET /debug/deliveries` |
| Muting threads | `thread_subscriptions` would just gain a `muted` flag |
| Grouping thread replies | Would reuse the same recompute pattern as DM grouping |
| Auto-read when viewing a message | Would mark activity read when a message becomes visible |
| Replay UI for dead deliveries | A `dead` status exists; replay just sets it back to `pending` |
| Replaying missed WebSocket events | Refetch on reconnect instead |
| Batching notifications, presence-aware rules | "Alice sent you 3 messages" as one push; skip pushes when the user is active |
| Typing indicators / presence | Not needed for the activity-feed story |
| Real auth | `?as=alice` user switcher |
| LISTEN/NOTIFY for the worker | 250ms polling is enough at this scale |
| Outbox cleanup | Would delete old events once all their deliveries are `done` |
| Broad test coverage | Four focused integration tests on the guarantees (§10) |

## 9. Build order: vertical slices, schema first

Vertical slices, so there's always something demoable. The one exception is **the whole schema up front**: changing the schema mid-build is the most expensive kind of rework, and a full schema is cheap to write. Later slices are the ones to cut if time runs short.

| Time | Slice | Demoable result |
|---|---|---|
| 0:00–0:20 | **Foundation:** `schema.sql`, pg pool, Fastify + Vite running, `?as=` user, minimal seed (users, channels, DMs, memberships) | App loads with a sidebar |
| 0:20–0:50 | **Messaging skeleton:** list/send (optimistic, idempotent), outbox + deliveries on every write, WebSocket broadcast, worker + search consumer + `/search` | Two windows chat in realtime; search catches up |
| 0:50–1:20 | **Threads, mentions, DMs, activity:** replies + thread panel, subscriptions, `computeRecipients`, activity consumer, feed UI with reason labels + read state, activity WebSocket push | Bob sees mention, reply and DM activity live |
| 1:20–1:40 | **Reactions + edit/delete:** grouped reaction activity, "(edited)", tombstones, read-time filtering | Full scenario except notifications |
| 1:40–1:50 | **Notifications + faults:** grace and staleness checks, fault env vars, debug endpoint, full seed through the domain service | Failure/retry demo |
| 1:50–2:00 | **Tests** | §10 |

## 10. Tests (integration, against real Postgres)

1. **Atomic write:** create → message + outbox event + 3 delivery rows exist, all from one transaction.
2. **Search convergence:** search fails → the delivery stays pending → the retry succeeds → the index has the latest version. Replaying an old version, or processing an edit after a delete, doesn't bring the message back.
3. **Activity idempotency:** processing the same event twice gives identical `activities` state.
4. **Grace delay:** a message deleted within the grace period → no notification is sent.

## 11. Demo script

Two browser windows, `?as=alice` and `?as=bob`, with `SEARCH_FAILURE_RATE=0.5`.

1. Alice posts in #engineering. Bob sees it instantly, with Alice's side optimistic.
2. Bob replies in the thread. Alice gets **participating** activity.
3. Alice edits her message. Bob sees "(edited)", and the feed shows the new text.
4. Bob and Carol react 👍. Alice sees **one grouped** reaction item.
5. Alice @mentions Bob. Bob gets a mention item, and a notification after 10s.
6. Alice @mentions Bob again and deletes the message within 10s. The item disappears and **no notification is sent**.
7. `/debug/deliveries` shows search failing and retrying while everything else is done. Search then catches up, and the deleted message is not searchable.
