# Hops: Implementation Plan

This plan puts `system-design.md` into practice. The phases match the build order in §9 of that doc. Each phase:
- has a **timebox**,
- ends in a **demoable state** with **acceptance checks**,
- names what to **cut if behind**,
- ends with a git commit, so the history shows the process.

Section references (§) point to `system-design.md`.

---

## 0. Ground rules and setup decisions

| Decision | Choice | Why |
|---|---|---|
| Runtime | Node 24 LTS (installed: v24.19.0; `engines` + `.nvmrc` enforce it) | Current LTS; required by the latest Vite 8 / Vitest 5; runs TypeScript via `tsx` |
| Package manager | pnpm (installed: 9.7.1), **single package** (no workspaces) | Fast, strict dependency resolution; single package keeps setup minimal; server, web and shared code all in one `tsconfig` |
| Server | Fastify + `@fastify/websocket` (wraps `ws`) | Quick to wire; the WebSocket shares the HTTP port |
| DB access | `pg` + hand-written SQL, `db/schema.sql` | No ORM or migrations to learn; the SQL is the design |
| Web | React 18 + Vite 8, Zustand store, plain CSS; TypeScript 7 for type-checking | Zustand fits the `messagesById` + ordered-ID-lists model (§5.3) |
| IDs | `uuid` package `v7()`, generated by the client for messages | Postgres 15 has no built-in uuidv7; v7 IDs sort by creation time |
| Tests | Vitest 5, real Postgres (`hops_test`), files run one at a time | The guarantees are about Postgres behaviour; mocking it would miss the point |
| Config | `.env` loaded by `server/config.ts` (dotenv) | Avoids Windows-specific syntax for env vars in package scripts |
| Dev | `pnpm dev` runs `tsx watch server/index.ts` and `vite` side by side (`concurrently`) | One command; Vite forwards `/api` and `/realtime` to `:3000` |
| Identity | `?as=<handle>` in the page URL → `x-user` header on HTTP and query param on the WebSocket | "Real auth" is on the cut list (§8) |

### Shared contracts (defined in Phase 1, extended as needed)

**HTTP API** (all under `/api`, user from the `x-user` header):

| Method | Path | Phase | Notes |
|---|---|---|---|
| GET | `/me`, `/users` | 1 | |
| GET | `/channels` | 1 | the user's memberships; `kind`, DM display name = other member |
| GET | `/channels/:id/messages` | 2 | last 100 top-level messages, each with `replyCount` |
| POST | `/channels/:id/messages` | 2 | `{ id, body, parentId? }`; idempotent |
| GET | `/messages/:id/thread` | 3 | root + replies |
| PATCH | `/messages/:id` | 4 | `{ body, expectedVersion }` → 409 on mismatch |
| DELETE | `/messages/:id` | 4 | soft delete |
| PUT / DELETE | `/messages/:id/reactions/:emoji` | 4 | returns absolute reaction summary |
| GET | `/activity` | 3 | `{ items, unreadCount }` |
| POST | `/activity/:id/read`, `/activity/read-all` | 3 | |
| GET | `/search?q=` | 2 | |
| GET | `/debug/deliveries` | 5 | counts by consumer/status + recent failures |
| POST | `/debug/faults` | 5 | *optional*: change fault rates at runtime |

**Message DTO:**

```ts
{ id, channelId, authorId, parentId, body, status, version,
  createdAt, editedAt, replyCount, lastReplyAt,
  reactions: { emoji: string; userIds: string[] }[] }   // absolute; client works out "mine"
```

A deleted message's DTO has `body: ""`. The server never sends deleted text.

**WebSocket events:**
- `message.upserted { message }`: sent to `channel:{id}`. Covers create, edit, delete, and the root message's `replyCount` changing.
- `reactions.updated { messageId, reactions }`: sent to `channel:{id}`.
- `activity.changed { unreadCount }`: sent to `user:{id}`. The client refetches `/activity` if the feed is open.

## Phase 1: Foundation (0:00–0:20)

**Goal:** an empty but real app. The schema, server, web app and identity all work, and a user sees their channels and DMs in the sidebar.

### Tasks
1. `git init`, `pnpm init`, set `"packageManager": "pnpm@9.7.1"` in `package.json`, install dependencies with `pnpm add` / `pnpm add -D`:
   - `fastify @fastify/websocket pg dotenv uuid zustand react react-dom`
   - dev: `typescript tsx vite @vitejs/plugin-react vitest concurrently @types/pg @types/react @types/react-dom`
2. `tsconfig.json` (strict, `moduleResolution: bundler`), `vite.config.ts` (proxy `/api` + `/realtime` with `ws: true` → `:3000`), `.env.example`:
   ```
   DATABASE_URL=postgres://postgres:postgres@localhost:5432/hops
   TEST_DATABASE_URL=postgres://postgres:postgres@localhost:5432/hops_test
   PORT=3000
   GRACE_MS=10000
   STALE_MS=900000
   SEARCH_LATENCY_MS=100-800
   SEARCH_FAILURE_RATE=0
   NOTIFY_LATENCY_MS=100-500
   NOTIFY_FAILURE_RATE=0
   ```
3. **`db/schema.sql`: the complete schema from §3 in one go.** Starts with `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`. Include every constraint and index, including `activities UNIQUE(user_id, group_key)` and the `event_deliveries(status, next_attempt_at)` index.
4. `scripts/db-reset.ts` runs the schema file. Scripts: `db:reset`, `db:reset:test`.
5. `server/db.ts`: `pool`, and `withTx<T>(fn: (tx) => Promise<T>)` with BEGIN/COMMIT/ROLLBACK.
6. `server/auth.ts`: a Fastify `preHandler` resolves `x-user` (a handle) to a user, or returns 401.
7. Routes `/me`, `/users`, `/channels`.
8. `server/seed/seed.ts`, **minimal version**: about 20 users (distinct handles, avatar = initials colour), 8 public channels (everyone is a member of most of them; a few channels are smaller, so "mentions of non-members are ignored" can be tested), 4–5 DM channels. **No messages yet.**
9. Web: `App.tsx` layout (sidebar | main | thread panel slot), `UserSwitcher` (changes `?as=` and reloads), `Sidebar` (Activity entry, Channels, DMs), `api.ts`.

### Acceptance
- `pnpm db:reset && pnpm seed && pnpm dev` works without errors.
- `http://localhost:5173/?as=alice` shows Alice's channels and DMs. `?as=bob` shows Bob's.
- Commit: `Phase 1: foundation`.

### Cut if behind
User avatars, so initials only. The channel membership differences (make everyone a member of everything).

## Phase 2: Messaging skeleton (0:20–0:50)

**Goal:** the full reliability path works for one feature. Sending is optimistic and idempotent, every write adds outbox and delivery rows, realtime works, the worker runs the search consumer, and search is queryable.

### Tasks

**Domain + outbox**
1. `domain/outbox.ts`: `enqueue(tx, type, messageId)`:
   - inserts an `outbox_events` row,
   - then inserts one `event_deliveries` row per consumer that handles `type` (from the registry),
   - the `notifications` delivery gets `next_attempt_at = now() + GRACE_MS`; the others get `now()`.
   - Consumer subscriptions:
     - `search`: Created, Edited, Deleted
     - `activity`: all four event types
     - `notifications`: Created, Edited
2. `domain/mentions.ts`: `parseMentions(body)` matches `/@([a-z0-9_.-]+)/gi`, removes duplicates, lowercases.
3. `domain/messages.ts`, `createMessage(tx, { id, channelId, authorId, body, parentId?, createdAt? })`:
   - Checks: the author is a member of the channel, the body is trimmed and 1–4000 characters, the parent is in the same channel and is a top-level message (one level of threads).
   - `INSERT … ON CONFLICT (id) DO NOTHING RETURNING *`. If nothing is returned, load the existing row: same author → return it (**idempotent retry**), otherwise throw 409.
   - Resolve mentions to users **who are channel members** and insert them into `mentions`.
   - `thread_subscriptions`: subscribe the author and the mentioned users to `rootId = parentId ?? id` (`ON CONFLICT DO NOTHING`). This follows §2.2's subscriber rule with one uniform insert per message.
   - `enqueue(tx, 'MessageCreated', id)`.
   - `createdAt` override is **for seeding only**. It isn't exposed through HTTP.
4. `listChannelMessages(channelId, viewerId)`: the last 100 top-level messages, oldest first, with `replyCount` and `lastReplyAt` (subquery or `LEFT JOIN LATERAL`) and reaction summaries. Written in one place as `toDto`.

**Routes + realtime**
5. `POST /channels/:id/messages` → `withTx(createMessage)` → **after commit** `hub.publish('channel:'+cid, message.upserted)`. For a reply, also publish the root's updated DTO (its `replyCount` changed).
6. `realtime/hub.ts`: on connect (`/realtime?as=`), subscribe the socket to `user:{id}` plus a `channel:{id}` topic for each membership. `publish(topic, event)` sends JSON and ignores closed sockets.

**Worker + search**
7. `fakes/network.ts`: `simulateNetwork(name)` waits a random time within the configured latency range, then throws `ExternalUnavailableError` with probability `failureRate`. Settings are held in a mutable object so tests and `/debug/faults` can change them.
8. `fakes/searchIndex.ts`:
   - `index(doc)`:
     ```sql
     INSERT INTO fake_search_docs … ON CONFLICT (id) DO UPDATE SET …
     WHERE fake_search_docs.version < EXCLUDED.version
     ```
   - `query(q, channelIds)` uses `ILIKE`, excludes `deleted`, and returns at most 20 results.
   - Both call `simulateNetwork('search')` first.
9. `consumers/search.ts`: load the message and call `index({ id, version, deleted: status === 'deleted', body: deleted ? '' : body, channelId })`.
10. `worker.ts`:
    - `start()`: a single-flight loop. Wait 250ms after each tick finishes, then run the next.
    - `tick()`: claims up to 50 due deliveries with the `SKIP LOCKED` query from §4.2, then runs them all concurrently with `Promise.allSettled`.
    - Local consumers (activity): `withTx(tx => handle(event, tx) + markDone(tx))`.
    - External consumers: `await handle(event)`, then `markDone`.
    - On error: `markFailed`, which sets `attempts + 1`, `next_attempt_at = now() + min(2^attempts, 300)s × (0.8–1.2 jitter)`, `last_error`, clears `locked_until`, and sets `status = 'dead'` once attempts reach 10.
    - Export `tick()` and `drain({ consumers? })` for tests and seeding.
11. `GET /search?q=`: restricted to the user's channel IDs, so DMs stay private. Results are joined with users and channels for display.

**Web**
12. `store.ts`: `users`, `channels`, `messagesById`, `channelOrder[cid]`, `threadOrder[rootId]`, `sendState[id]: 'pending' | 'failed'`.
    - `upsertMessage(dto)` applies **only if `dto.version >= local.version`**.
    - When inserting into an ordered list, avoid duplicates by ID and keep the list sorted by `createdAt`.
13. `ChannelView` + `MessageItem`: author, time, body with highlighted `@mentions`, and a pending look (dimmed) or failed look (red, with Retry and Discard).
14. `Composer` sends optimistically:
    - generate `v7()`, add the pending message to the store, POST it,
    - on success `upsertMessage(response)` and clear the pending state,
    - on error mark it failed. Retry re-POSTs **the same ID**.
15. `realtime.ts`: connect, apply `message.upserted`, and reconnect with backoff. **After reconnecting, refetch the current channel.**
16. `SearchBox` in the sidebar: results list, and clicking a result opens its channel.
17. Extend the seed: ~50 messages from `data.ts` templates through `createMessage` (a proper seed comes in Phase 5).

### Acceptance
- Two windows (`?as=alice`, `?as=bob`) on #engineering. Alice sends a message: it appears instantly for her (briefly pending) and for Bob in realtime.
- Send the same POST twice with the same ID (curl) → one row, same response.
- `select consumer, status, count(*) from event_deliveries group by 1,2` shows only `search` rows, all `done`. The activity and notification consumers aren't registered yet, so they have no rows.
- Searching for the new message finds it within about 1 second.
- Commit: `Phase 2: messaging skeleton with outbox, worker, search`.

### Cut if behind
The failed-send Retry/Discard UI (show "failed" only). Search result navigation.

**Note on the registry:** in Phase 2, only register the consumers that exist, so no delivery rows are created for unimplemented ones. Rows created before a consumer is registered are simply stale seed data, which `db:reset` clears.

## Phase 3: Threads, mentions, DMs, activity (0:50–1:20)

**Goal:** the core of the brief. Replies and the thread panel work, the attention rules are implemented, the activity consumer works, and the feed has reason labels, read state and live updates.

### Tasks

**Attention (§2.2)**
1. `domain/attention.ts`: `computeRecipients(tx, message)` returns `{ userId, reason, alert }[]`:
   - Returns `[]` for deleted messages.
   - **DM channel**: every member except the author → `dm`, alert. Stop here; mentions and threads in DMs are covered by the DM group.
   - **Mentions**: rows in `mentions` for this message, excluding the author → `mention`, alert.
   - **Thread reply** (`parentId` set): `thread_subscriptions(root)`, excluding the author and anyone already listed as mentioned → `participating`, no alert.
   - Priority: whichever of these rules matches first wins for that user. One entry per user.

**Activity consumer (§4.3): recompute from source of truth**
2. `consumers/activity.ts`, `handle(event, tx)`:
   1. Load the message and its channel.
   2. If the channel is a DM → `recomputeDmGroup(tx, channelId)`.
   3. Otherwise → `recomputeMessageGroup(tx, message)`.
   4. Always → `recomputeReactionGroup(tx, message)`.
   5. Collect the affected user IDs and return them. The worker publishes `activity.changed` to each **after commit**.

   **Shared upsert:**
   ```sql
   INSERT … ON CONFLICT (user_id, group_key) DO UPDATE SET
     reason, message_id, actor_ids, count,
     read_at = CASE WHEN EXCLUDED.latest_at > activities.latest_at THEN NULL
                    ELSE activities.read_at END,
     latest_at = EXCLUDED.latest_at
   ```
   Edits never mark an item unread again; new things do.

   | Recompute | Rule |
   |---|---|
   | `recomputeMessageGroup` | If deleted → delete every `msg:{id}` row. Otherwise, for each recipient upsert `msg:{id}` (`actor_ids=[author]`, `count=1`, `latest_at=createdAt`). **Delete `msg:{id}` rows for users who are no longer recipients** (a mention removed by an edit, and they aren't a participant). |
   | `recomputeReactionGroup` | Reactions on the message from people other than the author. None, or the message is deleted → delete `reaction:{id}`. Otherwise upsert it for the author: `actor_ids` newest first, `count` = number of reactions, `latest_at` = newest reaction's `created_at`. |
   | `recomputeDmGroup` | For each member `u`: the active messages from others in the channel since `u`'s current `read_at` (or all of them if there's no row). None and the row is unread → delete the row. None and the row is read → leave it. Otherwise upsert `dm:{cid}` with `message_id` = latest, `count` = that number, `actor_ids` = distinct authors, `latest_at` = latest `createdAt`. |

**Thread + activity API**
3. `GET /messages/:id/thread`: root (tombstone if deleted) + replies, oldest first.
4. `GET /activity` uses the **read-time filter from §2.4**:
   ```sql
   WHERE a.user_id = $1 AND m.status = 'active'
     AND (a.reason <> 'mention' OR EXISTS (SELECT 1 FROM mentions x
          WHERE x.message_id = a.message_id AND x.user_id = a.user_id))
   ORDER BY a.latest_at DESC LIMIT 50
   ```
   - Joins: actor users, channel, live body and `edited_at`. For replies, also the root's preview and status. For reaction groups, the distinct emojis from `reactions`.
   - `unreadCount` = the same `WHERE` plus `read_at IS NULL`. **One shared SQL fragment**, so the list and the badge can never disagree.
5. `POST /activity/:id/read` and `/activity/read-all` → update, then publish `activity.changed`. For DM groups, marking read also resets what counts as new: the next recompute counts from `read_at`.

**Web**
6. `ThreadPanel`: opened from "N replies" under a message. Shows the root and the replies, with its own Composer (optimistic, `parentId` set). Root tombstone: *"This message was deleted."*
7. `ActivityFeed` + `ActivityItem`. Each item shows:
   - an unread dot,
   - a **reason label** (GitHub-style): *mentioned you* · *DM* · *replied in a thread you're in* · *reacted*,
   - the actor phrase: "Alice", "Alice and Bob", "Alice, Bob and 3 others",
   - a live preview with "(edited)" when `editedAt` is set,
   - `#channel` or the DM name,
   - relative time,
   - reaction groups show the distinct emojis; DM groups show "sent you N messages".

   Clicking an item marks it read and navigates: to the channel with the message highlighted briefly, or opens the thread panel for replies and mentions inside threads.
8. The sidebar "Activity" entry shows the unread badge, updated live from `activity.changed`.
9. The mention composer is plain text. `@handle` autocomplete is **cut**.
10. Extend the seed: replies, mentions, DM conversations.

### Acceptance
- Bob replies to Alice's message → Alice's feed shows *"Bob replied in a thread you're in"* live, and her badge increments.
- Carol replies in the same thread → both Alice and Bob get an item. Carol doesn't get one for her own reply.
- Alice writes `@bob` in a reply in Bob's thread → Bob gets **one** item (*mentioned you*), not two.
- Alice sends Bob 3 DMs → Bob has **one** "Alice sent you 3 messages" item.
- `@dave` in a channel Dave isn't a member of → nothing for Dave.
- Commit: `Phase 3: threads, attention model, activity feed`.

### Cut if behind
Highlighting the target message when navigating (just open the channel or thread). The DM group count (show one item per DM message using `msg:` keys instead, and say so in the write-up).

## Phase 4: Reactions, edit, delete (1:20–1:40)

**Goal:** the remaining message actions, and their effect on the feed.

### Tasks
1. `domain/reactions.ts`: `setReaction(tx, messageId, userId, emoji, on: boolean)`:
   - insert with `ON CONFLICT DO NOTHING`, or delete,
   - `enqueue('ReactionChanged')`,
   - return the absolute summary.

   Route → publish `reactions.updated`. Reacting to a deleted message → 409.
2. `editMessage(tx, { id, userId, body, expectedVersion })`:
   - Checks: author only, not deleted.
   - `UPDATE … SET body, version = version + 1, edited_at = now() WHERE id = $1 AND version = $expected RETURNING *`. No row returned → 409 with the current DTO, so the client can undo.
   - Re-sync `mentions`: delete the rows that are gone, insert the new ones, subscribe newly mentioned users to the thread.
   - `enqueue('MessageEdited')`.
3. `deleteMessage(tx, { id, userId })`:
   - author only,
   - `status = 'deleted', version + 1`,
   - **the body is kept in the database but never serialised**,
   - `enqueue('MessageDeleted')`.
   - Deleting something already deleted returns success without doing anything, so deletes are idempotent too.
4. Routes → publish `message.upserted` (the tombstone DTO for deletes).
5. **Web:**
   - `Reactions` row: a chip per emoji with a count, highlighted if mine; a small picker with 6 fixed emojis. **Optimistic toggle**, undone on error, then the server's absolute summary replaces the local one.
   - `MessageItem` hover actions: react / reply / edit / delete (edit and delete only on your own messages).
     - **Inline edit**: optimistic, sends `expectedVersion`, undoes on 409 with a small "message changed — reloaded" note.
     - **Delete**: optimistic tombstone, undone on error. No confirmation dialog, to save time.
   - "(edited)" label next to the timestamp.
   - A deleted message renders as *"This message was deleted."* It stays in place if it has replies; otherwise it's removed after the tombstone has been shown once. **Decision:** keep tombstones for all deleted messages. It's simpler and matches Slack when there are replies.
6. Extend the seed: reactions, a few edits and deletes.

### Acceptance
- Bob and Carol react 👍 and ❤️ to Alice's message → Alice sees **one** item: *"Bob and Carol reacted 👍 ❤️"*. Carol removes hers → the item updates. Bob removes his → the item disappears.
- Alice edits a message that mentions Bob → Bob's feed item shows the new text + "(edited)", and **stays read** if it was already read.
- Alice edits out `@bob` → Bob's mention item disappears immediately (read-time filter). Once the consumer runs, it becomes a *participating* item if Bob is in that thread.
- Alice deletes a message → it disappears from Bob's feed immediately. In the channel it shows the tombstone. A thread root that's deleted keeps its replies.
- Two tabs edit the same message → the second gets a 409 and reverts.
- Commit: `Phase 4: reactions, edit, delete`.

### Cut if behind
The emoji picker (hard-code 👍 only). Optimistic edit and delete (non-optimistic is acceptable. Priority per §5.2 is send + reactions).

## Phase 5: Notifications, faults, full seed (1:40–1:50)

**Goal:** the last consumer, plus the things that make the reliability story demoable.

### Tasks
1. `fakes/notificationSender.ts`: `send({ idempotencyKey, userId, title, body })`:
   - calls `simulateNetwork('notify')`,
   - then `INSERT … ON CONFLICT (idempotency_key) DO NOTHING`,
   - and logs `🔔 → bob: Alice mentioned you: "…"` to the console so it's visible in the demo.
2. `consumers/notifications.ts` (§2.6):
   1. Load the message. If it's deleted → done (skipped, which counts as success).
   2. If `now - (editedAt ?? createdAt) > STALE_MS` → done (stale).
   3. Recipients = `computeRecipients` filtered to `alert = true`. Removed mentions are excluded automatically because this reads the current state.
   4. `send()` to each recipient with key `${messageId}:${userId}`. A partial failure means the retry sends to everyone again, and the idempotency keys remove the duplicates.
   5. Delay: already handled by `next_attempt_at` from `enqueue`.
3. `GET /debug/deliveries`: counts by consumer and status, the 20 most recent failures with `last_error`, and each fake's current fault settings. Optional `POST /debug/faults { search: { failureRate }, notify: { … } }`.
4. **Full seed** (§7) in `seed.ts`:
   - about 500 messages across channels with backdated `createdAt` (15 in the last 5 minutes, 50 in the last hour, 200 today, and the rest across the past week),
   - replies on about 20% of roots,
   - mentions in about 10% of messages,
   - reactions, a few edits and deletes, DM conversations.
   - All of it goes through the domain functions.
   - Then `worker.drain({ consumers: ['activity'] })` runs in the seed process, followed by `UPDATE activities SET read_at = latest_at WHERE latest_at < now() - interval '2 hours'`, so feeds look lived-in rather than 400 unread.
   - Search deliveries are drained by the server's worker when it starts (a visible catch-up is itself demoable). Notification deliveries are stale, so they're skipped.
   - Make the seed deterministic (a fixed random seed) so demos are repeatable.

### Acceptance
- Alice mentions Bob → the console shows the 🔔 line about 10 seconds later.
- Alice mentions Bob and deletes the message within 10 seconds → no 🔔. The delivery shows `done`.
- With `SEARCH_FAILURE_RATE=0.5`, `/debug/deliveries` shows search retries and failures while activity and notifications are all `done`. Search eventually returns the message.
- A fresh `db:reset && seed` gives a busy-looking app within a few seconds of starting.
- Commit: `Phase 5: notifications, fault injection, full seed`.

### Cut if behind
`POST /debug/faults` (env vars only). Reduce the seed to about 200 messages.

## Phase 6: Tests (1:50–2:00)

**Setup:** `vitest.config.ts` with `fileParallelism: false`. `tests/helpers.ts` resets `hops_test` using the schema, creates a few users and channels, and exposes `tick()`/`drain()` and the fault controls.

| Test file | Scenario | Checks |
|---|---|---|
| `write-path.test.ts` | Create a message; then create it again with the same ID | Message + 1 outbox event + 3 delivery rows (notifications `next_attempt_at ≈ now + GRACE`). The second create returns the same row and adds no new event. |
| `search.test.ts` | `failureRate = 1` → `tick()` → the delivery is pending with `attempts = 1`; set `failureRate = 0`, force `next_attempt_at = now()`, then `drain()` | The document is at the latest version. Then: edit → delete → **reset the edit's delivery to pending and process it again** → the document stays a tombstone (**no resurrection**). |
| `activity.test.ts` | A reply + reactions → process the same activity delivery twice (reset to pending in between) | `activities` rows are identical after the first and second run (**idempotent**). Mark read, then edit → still read. A new reaction → unread. |
| `notifications.test.ts` | Mention → delete before the grace period ends → force the delivery due → `drain()` | `fake_notifications_sent` is empty and the delivery is `done`. Control case: without the delete → exactly 1 row, still 1 after processing the event again. |
